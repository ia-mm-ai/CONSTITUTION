Deployment architecture and unresolved administrative boundaries

This document is a source-implementation design, not a deployment instruction
authorization. The crossing performs no Mainnet or Fuji act, L1 creation,
validator registration, public-network mutation, release, tag, or deployment.

Architecture inherited from the established diagnostic findings:
1. Avalanche supports blockchain creation with an arbitrary registered VM ID.
   This implementation is a custom, non-EVM, signed-event-sourced RPCChainVM.
   It is not a Subnet-EVM binary and cannot be substituted into stock EVM images.
2. Every validating node must receive the same custom executable, named by the
   VM ID derived through the pinned official AvalancheGo API. Node version,
   RPCChainVM protocol, executable hashes, configuration and genesis must agree.
3. An external Validator Manager can reside on C-Chain or another Warp-capable
   EVM chain. That control plane does not make this VM an EVM, supply missing
   validator custody, or confer constitutional authority. Selecting, configuring
   and validating a concrete manager remains separate work.
4. Builder Console stock Docker generation assumes Subnet-EVM. Custom-plugin
   provisioning needs a manual/CLI-aware path that distributes the executable
   to every validator. This repository supplies source and offline preflight,
   not a complete, qualified container deployment or a validator network.

Prerequisites for any later administrator-reviewed deployment:
- Fresh external advisory observations, reproducible binary provenance, explicit
  binary acceptance, and review of all unresolved qualification observations.
- Actual target network, genesis, validator set, node identity/custody and
  network membership parameters; no predecessor identity is reusable by inference.
- Deliberate external public-authority inputs distinct from private key custody.
- Complete custom-plugin distribution and RPC handshake on every validator.
- Validated manager location, Warp/message-verification assumptions, governance,
  L1 economics, operating balances and network-specific registration workflow.
- Durable disk, health monitoring, backup/recovery, restart/rejoin, state sync,
  consensus failure handling and upgrade/rollback qualification.
- Independent inspection of the State-derived representation and effect limits.

scripts/validator-preflight.py checks local executable hashes, official ID
filename, machine versions, Go/gRPC profile and protocol only. Inputs must be
independently trusted binaries and digests; the tool executes their version
commands. It neither contacts a network nor reads private validator keys.
Passing does not establish running node identity, custody, validator membership,
consensus health, installed plugin coverage, manager readiness or deployment.

The Source pair and canonical STATE remain controlling repository inputs.
Historical identifiers retained in lineage are references only. Historical
deployments, keys, receipts, artifacts, qualifications and predecessor reported
effects are not transferred to this implementation.

No READY_FOR_ADMIN_INSTANTIATION assertion is made. The explicit source status
set and each unperformed qualification are recorded separately in qualification.json.
